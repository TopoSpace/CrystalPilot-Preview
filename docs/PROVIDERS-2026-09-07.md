# 模型提供方配置：协议、认证与界面设计

> 对应本轮用户追加的提供方/密钥问题。配置工作包已实施并通过真实 HTTP 保存与浏览器验收；用户随后在 8010 自行填入两家密钥。主测试模型仍为 **gateway 的 GPT-5.6 Sol / xhigh**，保留 OpenRouter，不因这次测试不用它就删除它。目录检查与真实模型调用分别记录。

## 1. 为什么在 8010 看不到旧配置

本轮服务运行在新的 Git worktree，使用新建的 `workdir\audit-codex-home`。旧主安装的提供方与密钥并没有被删除；但隔离配置最初仅创建 gateway 且没有独立凭据。把预览切到 8010 后，没有同步展示两套配置的区别，造成了用户看起来像“原提供方和密钥丢失”的问题。

现已恢复 gateway 和 OpenRouter 两项定义，保持 gateway 为本轮测试默认。用户已在“设置 → 提供方与密钥”自行输入两家密钥，接口只核对 `has_key=true`，两个文件均受 Git 忽略规则保护。没有从主检出或个人 Codex 复制旧密钥，也没有在聊天、Git 或截图中展示密钥。gateway 的模型目录检查返回 HTTP 200、21 项；OpenRouter 未运行模型测试。

要区分三件事：

- **条目已保存**：有名称、接口地址和协议；
- **认证已配置**：本机确实有可供内核读取的认证材料；
- **模型可用**：选定模型的真实 Responses 请求（含必要能力）通过。

GET `/models` 成功只说明目录可达，不能把它当成流式推理、工具调用和图像输入都兼容。

**重新启动本轮预览时**，须继续指定这份独立配置，不能直接用另一个检出的默认启动方式，否则看到的仍会是另一套提供方。在本 worktree 根目录运行（8010 已运行时不要重复启动）：

```powershell
$env:CRYSTALPILOT_CODEX_HOME = Join-Path (Get-Location) 'workdir\audit-codex-home'
$env:CRYSTALPILOT_CPU_CORES = '2'
& .\.venv\Scripts\python.exe -X utf8 -m uvicorn server.app:app --host 127.0.0.1 --port 8010 --loop asyncio:SelectorEventLoop
```

这条命令不迁移主安装；配置和本机密钥仍不入 Git。正式部署的配置迁移按路线图 R0 单独验收。

2026-09-08 用户明确批准后，8010 已切换为独立后台进程，不再随当前 CLI 会话退出而终止。运行信息和实际监听 PID 记录在 `workdir\services\8010\service.json`，日志保存在同目录的时间命名文件中。停止/重启时先核对该 PID、创建时间、命令与端口归属，只操作这个服务，不能按 `python.exe` 名称批量结束进程。后台服务仍绑定本 worktree 和上述 CODEX_HOME；归档/删除工作区前应先停止或迁移。没有设置 Windows 开机自启，不保证机器重启后自动恢复。

## 2. 其他工具的设计参照

### Cline

[官方 OpenAI Compatible 配置](https://docs.cline.bot/provider-config/openai-compatible)将提供方、base URL、API key、model ID 分开，还说明上下文窗口、最大输出、图像/工具能力和价格等模型元数据。这些字段不能全部混进“提供方连接”表单。

### OpenCode

[官方 Providers](https://opencode.ai/docs/providers/)把认证与 provider 配置分开，支持 base URL、模型黑/白名单；多协议来自实际 AI SDK adapter，不是一个下拉框自动产生兼容性。

**借鉴**：基础信息优先，认证独立，高级项折叠，模型选择/能力另设层级。**不照搬**：它们的 SDK 支持范围不等于 Codex 支持范围，不为了“选项丰富”添加不可用的选项。

## 3. Codex 的协议边界

OpenAI 当前[官方源码](https://github.com/openai/codex/blob/main/codex-rs/model-provider-info/src/lib.rs)的 `WireApi` 仅有 `Responses`；`wire_api="chat"` 明确返回不再支持，其他值也不是可选协议。旧目录路径已变更，不能因为找不到旧文件就假设它仍支持 Chat。

| 对端接口 | Codex 配置态度 | 用户应怎么接 |
|---|---|---|
| OpenAI Responses | 原生 wire 格式 | base URL 指向可用的 Responses 服务；验证流式与工具能力 |
| OpenAI Chat Completions | 不当作当前内核原生能力 | 服务商需提供 Responses 兼容入口，或显式使用外部转换服务 |
| 旧 Completions | 非当前工作台的代理协议 | 不直接接入；单纯文本补全不能表达完整工具/状态流程 |
| Anthropic Messages | 不是 Codex 的原生 wire 协议 | 可使用实际支持 Responses 的提供方/适配网关访问 Claude 模型；不能把 Anthropic 原始 URL 填进去就声称支持 |
| OpenRouter | 已有 Responses 兼容入口 | 保留独立提供方及其认证；具体模型能力仍需验证 |
| Azure/企业代理 | 取决于端点实际协议与认证 | 配置 base URL、必要 query/header 和认证；Azure Identity/AWS 登录不凭 UI 开关虚构实现 |

“模型品牌”与“接口协议”不同：Claude 模型不必使用 Anthropic Messages，OpenAI-compatible 也不一定支持 Responses。协议兼容还包括 SSE 生命周期、工具参数、并行调用、取消、错误和图像格式。

本轮实际 worktree 内核为 pip 0.147.0。已有离线回归实际调用该二进制的 `features list`：Responses、请求/流重试及空闲超时字段解析成功，`wire_api=chat` 明确被拒绝。该探针的 CODEX_HOME 是无凭据临时目录，不访问模型服务。不能据此把最新源码所有其他高级字段也算作本版本验证通过。

## 4. 建议的配置界面

### 基础区（默认展开）

1. 预设：CrystalPilot gateway / OpenRouter / OpenAI / 自定义 Responses 服务。
2. 名称、稳定标识、base URL；明确填服务根地址，不含重复 `/responses` 或 `/chat/completions`。
3. 协议：OpenAI Responses；其他协议显示边界和适配方式，不作为可保存的假能力。
4. 认证方式：本机密钥 / 环境变量名 / 无需认证；原有命令认证或外部认证未显式更改时保留。
5. 密钥：输入框永不回填；空值表示保留，删除必须显式操作；状态显示“已配置/未配置”，不显示旧值。

### 高级区（按需展开）

- 请求失败重试、流重连重试、流空闲超时；明确单位、边界和留空沿用默认。
- 非敏感附加请求头；敏感认证头只给状态，不把保存值返回浏览器。
- 环境变量请求头映射：保存变量名，不保存/回显变量值。
- 查询参数，例如 Azure `api-version`；同样避免把密钥塞入可回显的字段。
- WebSocket、专有认证等只在实际内核支持且完成验证后开放。

### 模型层（不要挤入连接卡）

模型 ID、推理档位、上下文/压缩阈值、图像/工具能力、可见模型列表分别放到现有模型设置中。模型目录字段说明“服务方声明/本机覆写/实测验证”的来源；不能把手填超大上下文当实际可用额度。

### 测试层

- **检查模型目录**：无推理费用的可达性/认证/列表检查（以提供方实际计费为准），不贴“完全兼容”的成功标签。
- **测试模型**：显式选模型，使用极小、无项目数据的 Responses 请求；告知可能计费；不自动测试用户所有提供方。
- **能力验收**：工具调用、流式、图像/推理档位分别记录，不把一个文本回答等同于全能力通过。

整个页面保持短文案，技术原因放折叠帮助和文档。“当前项目使用”与“默认提供方”是不同状态，切换提供方对新线程生效，不伪装为正在运行的线程已立即迁移。

## 5. 必须修复的认证一致性

本轮读到一个直接影响 UI 配置可用性的缺口：提供方保存器可写入裸密钥，但旧 `print_token.py` 只读取 `Key:` 文本；这会出现“设置页已配置，内核认证却失败”。保存/状态检测/探针/auth hook 必须采用一致的解析规则，同时保留现有调用者检查。

编辑名称或 URL 不应悄悄把 env/命令认证改为另一种方式；更新显示字段也不应丢失原有请求参数。所有校验应先完成再写密钥/配置，避免保存失败却已破坏旧设置。

## 6. 中文问号问题的实证

本轮五个测试项目的显示名曾实际存成 `MOF-5 ? ????` 等，不是浏览器缺字。原因是命名时将含中文的 PowerShell here-string 管道给 Python，而 `$OutputEncoding` 为 `us-ascii`；设置 `PYTHONUTF8=1` 不能恢复在管道发送端已经丢失的字符。

已从 UTF-8 文件读取正确名称，再通过 HTTP JSON 写回，只修本轮创建的五个项目；逐项核对磁盘 Unicode 内容。后续中文批处理优先使用 UTF-8 文件或显式编码的 HTTP 请求，不再依赖默认 shell 管道。增加真实 API→浏览器中文名称回归，原子坐标、反射数据和原始路径没有改动。
