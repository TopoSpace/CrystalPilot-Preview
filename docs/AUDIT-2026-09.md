### Olex2 headless 缺口证伪：olex2c 一直都在（2026-09-01 凌晨）

- **旧结论作废**："win64 发行版无 olex2c、headless 只能等论坛/GUI 宏
  注入"是错案。`vendor/olex2/app/olex2c.dll` 本体就是 CONSOLE 子系统
  EXE 映像（PE 头 Subsystem=3），顶着 .dll 扩展名是更新器的载荷命名
  惯例（macOS 侧同理叫 olex2c_exe）。零 OpenGL/GDI/wx 导入=桌面零打扰。
- **四版冒烟迭代拿下驱动路线**：v1 管道 stdin 全灭（REPL 用控制台输入
  API，boot 完成后命令永不被消费）→ v2 ConPTY 可通但 PtyProcess.read
  阻塞、子进程死后包装脚本永挂 → v3 读线程+队列+quiet-break 全链可控，
  但 refine 内部 `user filepath()` 因相对 reap 迷路（"could not change
  current folder"，精修静默不跑）→ **v4 绝对路径 user+reap 全绿**：
  52s boot→reap→refine 4→file cif，"Refinement finished"。
- **数值验收**：olex2.refine（smtbx 引擎）在 probe_a（La/Ni 517 参数、
  103 约束、180 限制）上 R1_gt **0.0650** vs SHELXL 基线 0.0647，
  跨引擎 0.0003 内复现；4 圈 Max shift/esd 0.35，残差峰 ≤1.42 e/Å³。
  `file job.cif` 导出模型+数据 CIF（refine_ls 块须走完整报告周期，如实
  记边界）。
- **产品化**：crystalpilot/io/olex2c.py - Olex2Console（ConPTY spawn/
  读线程/quiescence pump/上下文管理）+ refine_job 一步式；教训链全文
  进 docstring；tests/test_olex2c.py 3 单测 + CRYSTALPILOT_OLEX2C_LIVE
  门控实弹测试。战略价值：olex2.refine 原生吃 HKLF5 孪晶精修（平台
  smtbx refine 工具拒收 HKLF5 的空白由此补上）+ 第三引擎交叉验证。
  后续候选：内置 socket server 模式（server start -p=8899）。

#### run_shelxt：报错字符串害得 agent 得出错误物理结论

- **实况**：两次都**没有失败**。`job.lxt` 白纸黑字，第一次

  16.61 Å）。SHELXT 在群搜索跑完前不写任何 .res，所以「超时」读起来

- **代价**：agent 据此判断 SHELXT 吃不下这个胞，退回电荷翻转，正是
  它自己的技能卡评为弱数据下更差的路线（0/6 成功）。**推理没错，
  错在推理所依据的证据是一句 "shelxt timed out"。**

  1. `all_space_groups=false` **不是提速手段**。元素表里有比 Sc 重的

  自启；solve-ladder 技能卡补两段执行模型（判读要点：**先看定相段是否
  完成，再决定加时还是换引擎**）。8 个单测，含对真实 r25 日志的回归。
- **可推广的教训**：**失败信息的信息量决定下游推理的质量**。

#### 查看器改造（三条并行，两个子代理）

- **生长变成一族状态**：后端 `hops` 1-4 与 supercell `n` 1-4 一直都在
  （routes.py 两处 clamp），前端却把 hops 硬编成 1、超胞只给 2/3，
  引擎已有的四分之三生长能力**没有任何途径可以请求**。现在
  非对称单元/生长/晶胞/超胞四族，各带自己的深度行；深度跨模式记忆，
  且**不清空手工生长的碎片**（server 的 `extra` 与 hops 正交）。
  实测 r25：26 → 42 → 69 → 82 → 101 原子单调生长。
- **侧栏从按钮墙变回网格**：15 个 overlay 原本是一条按构建顺序排的
  flat wrap，380 px 下每次换行位置都不一样。现在按**它们回答什么问题**
  分三行有标题的组（显示/关系/证据）+ 一行视图，标题列定宽对齐；
  一次性动作（带图提问/导出图/重置视角）与 aria-pressed 开关分开放。

  effect 因此把它的全部触发条件列成自己的超集，正确，但一次点击
  「多面体」触发 8 个 effect 和 8 次同步 WebGL 全场景重绘。真正的成本是
  重绘：`scheduleRender()` 用 microtask 合并（同一 commit 的 effect 在
  同一个 task 里跑完，microtask 在 paint 前排空），**8 次变 1 次，输出
  逐像素相同**。rebuild 触发器改成 render 期间派生的 generation
  计数器，**故意不用 state bump**：state bump 会把 rebuild 和图层拆到
  两个 commit，浏览器可以在中间 paint，每次结构切换所有 overlay 都会
  闪一帧。那是拿显示质量换性能，不做。

## 侧栏排版第二轮 + 孔道电子数其实是 smtbx 的缓冲区别名（2026-09-02）

### 一、卡片按文献的方式排字，不按 UI 的方式

第一轮拿到了布局，这一轮拿字。晶体学量（空间群、胞参数标签、
R₁/wR₂/GooF）改成斜体衬线，用无衬线排它们会让它们读起来像界面
装饰，而不是它们本身是的那些量；`--font-serif` 钉到 Cambria/Georgia
是为了 α/β/γ 的希腊字母覆盖。分子式给到 Olex2 给它的字号（19px）：
它是唯一一行说明「这是什么」而不是「精修得多好」的内容。胞参数改成
两列网格，标签带 accent 色，`a = b`、三个 90° 要能顺着列读下来，
那是每一次空间群论证的第一步，一行流水账把它藏起来了。

顺手删掉的和改对的：

- **原子数瓦片撤掉**。分子式已经说了一遍，状态行又说了一遍；在
  没有数据块的节点上它是四列网格里孤零零的一个框，读起来像布局
  坏了。位子给 Flack，那才是一个存在时值得一个瓦片的数。
- **GooF 0.94 → 0.96 原来画成红色下箭头**。GooF 定义上就该落在 1，
  这是**朝着**定义走。`RFactor` 加 `ideal`，并把箭头方向（数字往哪
  动）和颜色（那是不是对的方向）拆开，R 因子两者永远一致，GooF 不。
- 查看器右下角的场景计数并入卡片状态行（并带上范围）。它原来和
  晶胞轴三角标在同一个角，视口一矮就互相穿过去。

### 二、孔道电子数：smtbx 把同一块缓冲区发了两次

用户的直觉是对的，而且比表面看到的更深。`fft_map.real_map_unpadded()`
返回的是**同一块缓冲区**，所以 BYPASS 每轮末尾那句
`add_selected(mask > 0, f_000_s/V)` 在 `electron_counts_per_void()`
回读时还留在图里，只有循环**收敛**退出时才没有（break 发生在那句
add 之前）。逐变量实测（r25 n0030，用包住 `masks.miller.fft_map` 的
计数器数轮次）：所有未收敛的跑法，per-void 与 total 之比**精确等于**
`n_grid/(n_grid−n_solvent)`，三位小数吻合（240×240×100 是 4.836，
160×160×72 是 4.717）；唯一收敛的那次是 1.000。

修正按每个孔洞的格点数按比例扣掉多余量，注入项本身按格点均匀，
所以这在未收敛时是精确的，在收敛时是恒等变换。mvp-sjtu9 n0013：
per-void 5320.9 → 2014.7，记录的 total 是 2015.9。

**真正要命的是这个数也是 agent 读的那个数。** `solvent_mask` 报的
是未修正的 raw，而工具自己的描述让 agent「对照 H2O 10 e、MeCN 22 e、
DMF 40 e」去认溶剂。r25 n0022 上那读出来是 1192.9 e，约 30 个 DMF，
真值 296.9 e，约 7 个。同一个 helper 现在被显示路径和工具共用
（`mask_tools.consistent_void_electrons`，scene.py 只是别名，配一条
「共用同一实现」的测试），差 5 倍的两套说法不可能再分叉。

顺带白捡一个 smtbx 不给的东西：**多余量只在循环耗尽 max_cycles 时
存在**，所以它的出现本身就是收敛报告。`solvent_mask_converged` 因此
是免费的，而它是更有后果的那一半，未收敛的 f_000_s 还在爬
（r25 实测 10 轮 1241.7 e、12 轮 1258.0、40 轮 1549.7），拿它当溶剂
组成是把下界当测量值。

另有两个查出来但没有动的事实：显示路径原来只转发 6 个 mask 参数中的
2 个（单是 d_min 就把网格和体积挪了）；而 `run_shelxl` 节点的

### 二、四个最贵的浪费都是工具对模型说了错话

1. **`solve_superflip` 从 r16 起 17/17 从未成功，pa1 一批烧 4,991 s**。根因
   本轮二分找到：子进程继承了 MCP 服务器的 stdin 管道，stdio 传输线程在

### 二、根因（全部工具侧，全部已修）
